# 原神地图叠加（genshin-map-overlay）

在**游戏内大地图**画面上叠加 bilibili wiki 的全地标点位：靠图像特征匹配自动对齐，
不需要手动校准。`F8` 切换显示，`F9` 强制重新定位。

> 状态：**实验性（0.12.0）**。定位算法与坐标标定已离线验证（误差 <1px），
> 但依赖宿主提供 opencv wasm 与画面读取权限，见下文"前置条件"。

## 前置条件

| 依赖 | 说明 |
|---|---|
| `minAppVersion` 2.16.0 | 需要宿主支持 `permissions` 与 `assets`（带 sha256 校验的大资源） |
| `wasm` 权限 | ORB 特征匹配由 opencv wasm 提供 |
| `frame-capture` 权限 | 需要把游戏画面读回像素做匹配 |
| 画面可读 | 若云游戏画面是受保护 `<video>`，`getImageData` 会抛 `SecurityError`，插件会显示"画面不可读: TAINTED"并停止 |

自检画面是否可读：开启后看右上角 HUD，或控制台执行
`window.__miguMapOverlay.grab()` —— 返回 `{err:'TAINTED'}` 即不可用。

## 工作原理

1. 随插件发布的 Wiki `map-6.7/1` 地面层预拼底图（3072x2048，sha256 锁定）在 worker 里算一次
   12000 个 ORB 特征（`vendor/fit_worker.js`，主线程零阻塞）；
2. 抓取游戏画面一帧，**缩到与底图相同的尺度**（用上次定位的缩放当先验；
   首次定位扫多档金字塔）转灰度，算 ORB 特征后只与上次位置附近的底图
   特征子区做 knn 匹配 + RANSAC（内点率闸门拦掉噪声假解）；
3. 得到「画面 ↔ 底图像素」的相似变换，反解后把点位投影到画面坐标绘制；
4. 帧间用光流（calcOpticalFlowPyrLK）连续跟随拖动/缩放，累计漂移超阈值
   自动触发一次重定位。

## 取帧管线（0.9.3 起）

跟踪的硬成本不是算法而是**取帧**：主线程每帧 `drawImage(video→canvas)` 要把
GPU 纹理回读到 CPU，真机实测中位 **13.9ms**，20Hz 跟踪即 278ms/s，
每帧 16.7ms 的预算被吃掉大半 —— 这是"拖地图掉到 30fps"的根因。

0.9.3 起改用 `MediaStreamTrackProcessor` + `OffscreenCanvas`：worker 直接从视频
轨道读 `VideoFrame`，缩放取灰度后把 buffer 零拷贝转移回主线程，主线程完全不
参与取帧。worker 源码是 `vendor/grab_pump.js`（sha256 登记、宿主校验）。

CDP 采样分析器实测（真 video 靶场，拖动 12s，全 13 类 7118 点，即当时的全量数据）：

| | 改前 | 改后 |
|---|---|---|
| `drawImage` selfTime | 111.7ms/s | **2.2ms/s** |
| `getImageData` | 27.1ms/s | 不再出现在主线程 |
| 主线程空闲 | 0.6% | **49.9%** |
| 页面 FPS | 43.4（canvas 靶场） | 56.1 |

**背压**：worker 只在主线程发 `{type:'want'}` 后才处理下一帧，否则会按流帧率
一直算，等于把浪费从主线程搬到 worker，CPU 照样烧。

**回退**：帧泵起不来时自动退回主线程 `grab()`，功能不受影响（只是慢）。
已实测三种回退场景全部正常（`probe/test_pump_fallback.py`）：
旧 WebView 无 `MediaStreamTrackProcessor`、`<video>` 无 `srcObject`（MSE/HLS）、
画面是 `<canvas>`。`window.__miguMapOverlay.pumpInfo()` 可查当前模式与原因；
`trackGrabs > 0` 即表示取帧退回了主线程。

注意重定位（ORB）路径仍走主线程 `grab()`：它需要 960px 宽帧且频次低
（实测 0.4 次/秒），不是热路径。

## 标定（改动前必读）

以下常量由实测确定，改错会导致整体错位：

- **瓦片 Y 轴翻转**：站点自定义 `getTileUrl` 中 `y = -coords.y - 1`。
  拼图必须在 Leaflet 瓦片空间进行，`urlY = -leafletY - 1`。
  错过这一步时地图看起来依然"连贯正常"（镜像后海岸线自然），
  只有把点位叠上去核对才会暴露 —— 所以务必用点位验证，别只看底图。
- **坐标变换**：WGS84 → `+proj=merc +a=6378206 +b=6356584.314245179` → `×0.0004883406312203475`，
  y 取反。点位若带 `version==4` 则已是 wiki 坐标，跳过变换。
  验证方法：在 wiki 页面控制台跑
  `mapPackage.convertLatLng({lat:"25.5558",lng:"-7.414138"},0)`，应得 `{lng:-403,lat:-1429}`。
- **Leaflet 投影**：`CRS.Simple` + `L.Transformation(0.0078125,0,0.0078125,0)`，
  `pixel = 0.0078125 * coord * 2^zoom`。
- 参照拼图范围：z=5，Leaflet 瓦片 x∈[-16,7]、y∈[-8,7]。
- 底图版本：`map-6.7/1/tiles-G`。Wiki 更新地面瓦片版本后必须重新拼图；即使
  瓦片坐标范围不变，旧图也无法匹配新区域（实测旧图仅 4–5 内点，新图 35 内点）。
- **帧→屏幕几何**：视频按 `object-fit` 摆进元素盒，**内容矩形 ≠
  getBoundingClientRect**。必须用 main.js 的 `contentBox()` 换算；拿元素盒
  直接换算时，信箱黑边会变成整体尺度+平移偏移（真机实测 0.796 倍 +139px，
  内点率完全查不出来——ORB 只证明 帧↔底图 自洽）。验证探针：
  `probe/abs_accuracy.py`（真实截图）与 `probe/e2e_letterbox.py`（端到端靶场）。

## 数据

`data/points.json`：**504 个分类、56331 个点位**，覆盖 wiki 地图工具的全部可用分类。
`data/icons.json`：每类的官方图标直链（patchwiki CDN）与大类分组。

采集自 bilibili wiki 的 `Data:Map4/type/json`（分类表，565 类）与
`Data:Map4/type/<id>/json`（逐类点位）。565 类里 **504 类有数据**，
其余 61 类是分类表登记但数据页 404 的空类（如部分未实装内容）。

点位格式（后三项按需附加，绝大多数点只有前两项）：

```
[lng, lat]                      // 地面层、无名称
[lng, lat, layer]               // 地下/上层：B1..B7 / A1..A5
[lng, lat, layer, title]        // 有名称
[lng, lat, layer, title, id]    // 有说明，id 可取 Data:Map/point/<id>
```

层级分布实测：G(地面) 52266、B1 2477、B2 925、B3 400、B4 130、A1 66、其余零星。
旧版直接把地下层点位整体剔除，现在带上 `layer` 由渲染层决定显示哪层。

带名称的点 166 个(0.3%)、带说明的 657 个(1.2%)——所以附加字段几乎不增加体积
（仅坐标 752KB vs 带名称 765KB）。**说明内容不预置**：wiki popup 里的说明
（多为一张图，如 `[[File:地方传奇-湖畔的维维安涅-s2uayie0zu.png|600px]]`）
需要按 id 请求 `Data:Map/point/<id>`，点击时按需拉取，不随插件发布。

数据来源：bilibili wiki 原神地图工具（CC BY-NC-SA），仅作只读展示，不修改、不上传。

### 规模与性能（换数据前实测）

点位数 ×7.9、体积 115KB→798KB，两项风险都测过：

| | 旧(13类7118点) | 新(504类56331点) |
|---|---|---|
| `draw()` 中位 / P95 | 0.8 / 2.3ms | 2.0 / **6.0ms** |
| 拖动 FPS（全开） | 58.3 | 49.6 |
| `JSON.parse` | 1.2ms | **20.3ms** |
| 面板图标请求 | 15 | **22**（懒加载后） |

最坏情况（用户勾选全部 504 类）`draw` P95 仅 6ms，仍在 60fps 的 16.7ms 预算内。
默认只开 2 类时 `draw` 0.1ms。

图标必须懒加载：504 个 `<img>` 一次 eager 会并发 **493 请求 / 3.4MB**，
实测造成 666ms longtask，足以卡住云游戏串流。改用 `IntersectionObserver`
（`root` 为列表容器）后降到 22 请求 / 264KB。
注意不能用 `loading="lazy"`——面板折叠时行高为 0，浏览器判定"不在视口"
就永远不发请求，展开后仍是空白。

启动期另有一个 600~800ms 的 longtask，**与本次扩容无关**：同一份代码换回旧数据
实测 728ms（新数据 837ms），来源是 `ensureReady` 里对 3072x2048 底图
（6.3Mpx / RGBA 24MB）分块 `getImageData` + 转灰度，0.9.x 起就存在。

### 点位说明弹窗（0.12.0）

点击带**白色细圆环**的点位可查看 wiki 说明（图片 / 文字 / 参考视频）。
`Escape`、再次点击同一点、或点击空白处均可收起。圆环只在放大到不聚合时
才画——聚合态下单点不单独绘制，画环会变成"环浮在簇旁边"的错位。

说明来自 wiki 的 `Data:Map/point/<id>` 页面，与点位字段里的
`content/imageLink/videoLink` 是**两套东西**。这类页面共 24161 个，但其中
17359 个是占位符（"欢迎在下方留言~"、贡献者标签、空模板），
**只有 7436 个有实质内容**——所以只给这些点建索引并画圆环，
否则用户点开一片空白，比没有功能更糟。

`data/descs.json`（850KB / 7130 条：含图 4685、含文字 2627、含视频 1430）
与点位分开发布：只服务 12.7% 的点，塞进 `points.json` 会让每次定位都白
解析它。加载失败不阻塞定位与绘制，只是点不开说明。

内容清洗踩到的四类 wikitext（处理见 `probe/harvest_descriptions.py`）：

| 形态 | 不处理的后果 |
|---|---|
| `#重定向 [[Data:Map/point/xxx]]`（106 个） | 把 "#重定向 Data:Map/point/23u1..." 当说明显示给用户 |
| `{{宝箱\|id=..\|提示=..}}` 多行模板 | 单行正则漏掉 171 条，整坨模板源码显示出来 |
| `{\| class="wikitable" ... \|}` 表格 | 与 `{{}}` 是两套语法，残留 41 条 `style=...` 代码 |
| `{{颜色\|...` 未闭合模板 | 半截模板混进正文 |

其中 `{{宝箱}}` 的 `提示` 字段是**真正有用的说明**（6939 个宝箱页里 884 个
非空），整体丢弃模板会把最有价值的信息一起扔掉，必须单独提取。

**事件模型（最容易出事的地方）**：叠加画布是 `pointer-events:none`，
点击必须照常传给游戏，否则地图拖不动、技能放不出——那是从"少个功能"
变成"游戏没法玩"。所以不给 canvas 开 `pointer-events`，而是在 `window` 上
捕获阶段监听 `pointerdown`，**命中才吞事件**，其余原样放行。
`probe/test_desc_popup.py` 把"空白处点击必须传给游戏"作为硬断言。

弹窗定位必须在图片加载后重算：说明图原始尺寸可达 1920x1080，插入时
`<img>` 高度还是 0，只量一次会让弹窗在图到达后顶出屏幕底部。
这个缺陷自动化断言没覆盖到，是**人工看截图**发现的；现在每张图 `load`
后重新摆位，并限制 `maxHeight` + 内容滚动，`test_desc_images.py` 增加了
屏幕四角的越界断言。

## 已知限制

- 需要游戏内**大地图**处于打开状态；在普通游戏画面上定位会失败（属预期）。
- 地下层地图暂不支持（只叠 G 层）。
- 平移/缩放由光流自动跟随 + 自动重定位；`F9`/面板「重定位」仅在跟丢时救急。
